How that is known, and the check that does not work

The evidence is the function's LastModified timestamp, which UpdateFunctionCode bumps — so code committed on 31 August cannot be in a function last written on 26 August. That is solid, but it is an inference rather than an observation, and it is worth saying which.

The obvious way to confirm it does not work. An unauthenticated POST to /rest/recipes/:id/adapt returns 401, not 404 — and so does POST to a path that has never existed under that prefix. Auth is applied at the mount in the MOUNTS loop, so it answers before Express ever tries to match a route, and a missing route is indistinguishable from a present one. Confirming this needs a real bearer token, at which point an absent route falls through the recipes router and 404s properly. Verified against the live function URL, both cases.

02

The loop, and what sits under it

The fridge, the week and cooked history are usually costed as three features. They are one feature with three entry points, because each one supplies the next one's hardest input — and all three were unreachable until find_recipes could rank by ingredient rather than filter by it. It can now, in the working tree: what follows is why that mattered, and item 04 records what was actually built.

Every ingredient path in this database is a conjunctive filter: a recipe qualifies only if it contains every id passed in. Point a fridge at that and it inverts — ten items returns almost nothing, thirty returns zero, and it gets worse the more the user invests. A fridge is a ranking input, and nothing here can consume one.

Which is why overlap ranking was the safest expensive thing on the list.

It is the precondition for all three loop items, and it independently closes a defect that is already costing you: of 1041 ingredients only about a third are referenced by any dish, so two thirds of the ingredient picker is a trapdoor that empties the results. 20260830000002 sorted the picker to route around that hole. It did not close it. This does — even if you never build the planner.

Written on 2 September, and it was worse than the figure above. Measured against the dev catalogue with a 26-item fridge fed in the most generous order possible — the catalogue's most-used ingredients first — the AND filter returns 100 rows at one item, 53 at two, 29 at three, 2 at four and 0 from five onward, and never recovers. Not thirty items. Five.

04

Overlap ranking — written

20260902000001_pantry_overlap_ranking. find_recipes takes p_pantry uuid[], which ranks and never filters — same rows, same totals, same facets, different order — and returns pantry_have, pantry_missing and the missing ingredients by name, the shape find_near_miss_recipes already uses for diets.

The advice above was followed, and one thing was added to it. ingredients keeps its AND-all semantics: the decisive caller turned out to be the client's own generation trigger, which fires off a short page — widen the filter and every page is full, so the search screen quietly stops generating. What did change globally is the identity closure: ingredient_identity_ids folds each id together with every ingredient row that is the same thing, on ingredients, blacklist and p_pantry alike. Strictly widening for a filter, strictly narrowing for a blacklist, so no caller loses anything. Picking “All Purpose Flour” reached 1 dish before and 76 after; Red Pepper Flakes and Risotto Rice reached nothing before.

The ranking is fewest-missing, not most-used, with the fridge's own contribution as the tiebreak and a clause that sinks any dish the fridge did not reach at all. No weighted score: a weight would be a fitted constant with nothing to fit it against, and it could not be printed on a card. Staples (pantry_staples, a table of canonical ids) are exempt from both sides — they are 17.7% of ingredient rows and spread 0–4 per dish, so counting them is noise with variance.

What is left. Apply the migration to the dev project, and give the client something that passes the parameter — item 07 is what would. Until then this changes nothing anybody sees, by construction: with an empty pantry the ordering is byte-identical to before, which check-pantry-ranking asserts first of its 23 cases.

The week — plan as an annotation

plan_id + plan_slot + a title on shopping_lists, mirroring 20260819000001 exactly, then a filter parameter on useEverythingToBuy. That is the whole first version.

It is cheap because the hard part is shipped: the aggregated list already merges any number of recipes, keyed on ingredient id, grouped by aisle, scaled by servings, ticked across dishes, offline. A plan must not be a menu — menus are shared community rows unique on (main_recipe_id, dish_signature), so two users planning the same five dinners would silently share a plan, and it would surface on the home feed.

Slots, not dates. Cook Thursday's dish on Tuesday and a dated plan is wrong in two places; an ordered set does not notice. Deviation then costs nothing by construction rather than by design.

06

Sum amounts within a unit family — written

Done in round-quantity.ts, beside formatScaledAmount, because a total is an amount becoming text and assembling one anywhere else would round by its own rules. UNIT_META gained a family field mirroring units.type; sumScaledAmounts groups by it and mergeMenuIngredients calls it.

“Collapse countables” was wrong, and the units table is what makes it dangerous. Every count unit carries base_unit_id → piece, conversion_factor 1.0, so following the table's own conversion turns a pinch of salt and two cloves of garlic into 3 pc. That factor is a storage convention, not a claim. Count units sum only with an identical unit — as does any abbreviation the table has never seen.

Across the whole catalogue merged as one list: 345 amount terms become 191, and 142 of 165 lines now carry a single number. Salt was a 22-term chain and is now 22 tsp + 4 pinch + 16 g. The 23 lines that keep a + keep it for a reason a shopper can act on — grams of flour beside cups of it, a bunch of parsley beside eight sprigs — and that + is now a statement rather than a default.

It did not need item 05 after all. That caveat assumed a menu was the only place amounts merge; “everything to buy” already merges every recipe on every list, which is a larger set than any menu. The twelve-dish case has existed the whole time.

Paid plan generation

Pick five dishes that fit the diet, the skill level and the weeknight time band, chosen partly for what they share so the shopping list is short. Catalogue-first — a plan assembled from find_recipes hits costs nothing to fill; generation is the fallback for slots retrieval cannot answer. Three that look like quick wins and are not

Turning on Sentry. It reads as setting an environment variable, and it is not: @sentry/react-native is a native module in a CNG project with ios/ gitignored, so it costs a prebuild, a full native rebuild and fresh EAS credentials — and that price recurs for every contributor. Real work, worth doing, but never schedule it for an afternoon and never for release day.

The purchase-to-webhook fallback. I estimated half a day in the first version of this document and I would not stand behind that. The code is small; the design is not. The actual work is the bounding rule: what stops it calling RevenueCat on every 402 for every non-payer, forever. Budget a day, and decide the bound before writing anything.

Committing the client working tree. 111 changed files across a dozen features — the cook-step redesign, the onboarding restructure, the new preferences feature, the storage module. That is a review problem, not a build problem, and it does not compress into an afternoon. It also does not block the deploy above; the two are independent. What it blocks is the next EAS build.

06

Deliberately not building

A roadmap that recommends everything recommends nothing. Each of these was in a source document; each is out, and the reason matters more than the verdict.

Gamification
Out, your call. Nothing in this app's design argues for it — the product is careful never to promise what it cannot keep, and streaks are a promise about the user rather than about the food.
The ingredient affinity view
Waits on two things: the dedupe finishing, and a database you intend to wipe. Affinity is computed over the corpus — building it now means measuring a catalogue that is about to be deleted and keeping the answer. Cheap to build later; the migration and the read are a day. Not now.
“Buy this, unlock N dishes”
Measured: the best possible purchase unlocks two dishes, and only 7 dishes in the whole catalogue sit one ingredient away. That is a catalogue-size problem, not a query problem. The same query read the other way — “3 dishes are one ingredient away” — is the honest version, and item 04 now returns exactly that: pantry_missing with the missing ingredients named.
Multi-hop substitution
There is no substitution graph to walk, and both ways of manufacturing one were tested and failed. Embedding kNN on Butter returns Butter Bean, a legume. Don't build it on this evidence.
Reading prompt history as preference
29 rows, one profile, and they are dish requests — nobody has typed “I don't like coriander” and nobody will, because that is what the blacklist screen is for. Cuisine affinity is the one honest signal in there, and its threshold is profile count, not row count. Three orders of magnitude away.
Turning on the taste profile
The review date is 2026-09-13 and the data already answers it. Two signals clear the threshold and they are the same axis pointing both ways — harder ×3 and easier ×2 — which reads back as “take the technique further; keep it plain”. Difficulty was never a standing preference; it is a per-dish decision with a first-class home in settings already. Recording it as a taste signal was the design error, not the threshold.
Leak 3 as a “taste” ranking term
Real, but the fix is not a new signal. find_recipes ranks on skill level and everyone's favourite count, and there is nothing revealed worth adding (see above). The right first addition to that ORDER BY is overlap — declared, explainable, and item 04 has now made it: three integer keys between the skill tier and the like count.
Dates on the plan
A calendar creates the failure it is meant to prevent. This is a deviation argument, not a shortcut — and it is why the week is cheap.
Skia, three.js, any 3D
All six motion items shipped without a new dependency. The identity is painted, ios/ is gitignored, and a native add costs a prebuild and fresh credentials for every contributor forever. Settled.
The deep health-check probe
Proposed when there were zero alarms. The metric-filter alarms on fault=service are live and verified firing, so a token-spending probe now duplicates coverage you already have. The real prevention is auto-recharge on the OpenAI billing page, which no amount of AWS alarming replaces.
Automatic failover to Bedrock
It has never run end to end — Anthropic models are gated on the account. Failing over to an untested path during an incident is how one outage becomes two. Worth making real as its own work; never worth an automatic trigger.
A drinks taxonomy
The gate is done and covered by evals. Giving drinks a home needs a drink course tag and a dish_form value — a migration and a seed change, not a prompt edit. Nothing is asking for it.
Sharing an imported recipe
Would need a signed, expiring token through an authenticated route. /share is open because its caller is not the app, so there is no session to compare an owner against. Real work, no demand.
The SNS email subscription
Excluded at your request — you are aware and it is yours.
